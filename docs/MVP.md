# GSCleaner MVP 验证方案

> 目标：先在官方场景验证单目标删除与修复，再在同一场景尝试一次多目标清理，判断现有技术能否支持“用户选出多个干扰物 → 统一删除 → 背景修复”。
>
> 本文是首轮技术验证方案，不是最终产品设计。首轮只验证完整数据条件下的背景清理，不实现编辑器、通用适配器、自动候选或 PLY-only 高质量修复。

## 1. MVP 要回答的问题

给定一个或多个**由用户人工确认**的删除目标：

1. 仅删除目标后，是否会误删目标周围的背景？
2. 官方 Inpaint360GS 修复是否比“仅删除”更接近真实的清场背景？
3. 修复是否破坏了原本没有被编辑的区域？
4. 多目标删除时，是否误伤目标之间需要保留的背景？虚拟视角是否覆盖全部修复区域？
5. 主要失败来自目标归属、空洞判断，还是补全质量？

单个场景只能形成局部结论：成功说明值得在更多场景继续，失败说明当前配置或方法在该场景上不成立，不能直接推广到所有场景。

## 2. 固定范围

### 使用的数据

**MVP-A（先做）**：选择一个官方 `inpaint360` 场景，先指定一个目标，不引入周围物体的临时移除；要求数据目录同时包含：

- 带干扰物的训练图像、COLMAP 相机和官方配置；
- `test_IMG_*` 清场后的图像，用作真实背景参考；
- 数据目录中的 `unseen_mask`，用于修复区域评测；它是否确实是人工核验的清场区域，必须在运行前检查。

开跑前必须完成以下核验：

1. 打开 `data/inpaint360/<scene>/unseen_mask/` 中的样例，确认它确实标出清场区域，确认 mask 极性、分辨率和文件名覆盖范围；不能默认它等同于运行时生成的 mask。
2. 对照 `test_IMG_*` 的命名确认有可比较的清场视角。若 `unseen_mask` 只覆盖虚拟视角，Run 1 不能直接获得同等区域指标，必须调整评测设计。
3. MVP-A 只指定一个删除 ID，暂不设置 `surrounding_ids`，避免周围对象恢复分支改变 Run 1 的输出语义。

官方代码对 `inpaint360` 数据会把包含 `test` 的图像排除在训练图像之外，并在 `--eval` 下从带物体图像中按 `llffhold=8` 留出测试视角。运行时不要改动官方数据布局或绕过这套划分。

`unseen_mask` 有两条可能的来源路径，不能混为一谈：数据集目录中的
`data/inpaint360/<scene>/unseen_mask/` 是评测参考；运行修复流程生成的
`inpaint_2d_unseen_mask_virtual/` 是管线中间产物。后者不能自动视为真实 GT，
也不能用管线自己生成的 mask 证明管线输出正确。开始 Run 0 前应打开几张数据集
`unseen_mask`，确认文件名能覆盖计划评测的 `test_IMG_*` 视角，确认前景/背景
极性、分辨率和区域含义，并把这次核验结果记录下来。若 mask 只覆盖虚拟视角，
必须调整评测设计，不能声称 Run 1 也有同等区域评测。

这里有两类评测参考：

- `test_IMG_*`：清场后的真实图像，用于判断背景恢复是否接近真实结果；
- `--eval` 留出的带物体视角：用于检查未参与优化的原始场景视角上的一致性。

它们不是同一个测试集，必须分别记录。

**MVP-B（A 完成后）**：优先复用同一场景，选择 2–3 个确实存在、能从分割标签中辨认的不同对象。先验证相邻目标；如场景允许，再检查相距较远目标的修复覆盖。必须核对清场参考是否真的移除了**全部**所选目标；如果只提供了单目标清场参考，则多目标实验仅评估删除正确性、保持度与跨视角连续性，不能声称多个空洞的真实背景恢复已得到 GT 验证。不为凑数量而更换数据或建立新数据集。

### 暂不实现

- SuperSplat/LichtFeld 集成和 UI；
- `RemovalAdapter`、稳定 ID 谱系和通用 schema；
- 自动发现干扰物；
- PLY-only 的高质量补全；
- 阴影、反射、重光照和碰撞 mesh；
- 完整产品阈值和跨场景统计结论。

## 3. 两轮验证：MVP-A 单目标 → MVP-B 多目标

先完成并判断 MVP-A，再决定是否执行 MVP-B。两轮都沿用下述 **Run 0 / Run 1 / Run 2** 对照；每轮内部必须使用相同场景、对象感知 checkpoint、最终冻结的目标集合与可比的相机设置。MVP-B 不要求重新训练 Run 0，可复用 A 的 checkpoint，也不阻塞 MVP-A 的单目标结论。

### 目标怎么选（MVP 不开发编辑器）

1. 先运行官方 `run_seg.sh`，打开 `data/inpaint360/<scene>/images_<resolution>_num/` 下带编号的图像；编号由 `tools/add_label_num_hqsam.py` 根据 `associated_hqsam` 标签图绘制。
2. 在几个不同视角交叉确认每个对象的编号，并明确记录 **Remove ID 列表**；其余对象默认保留。遇到同物体跨视角关联错误、边界混杂或目标无法确定，先人工修正或记为分割失败，不能把错误标签当成有效目标。
3. MVP-A 选一个编号；MVP-B 选多个编号。例如，在官方 `run_remove.sh` 中使用 `target_id="5,12,26"`，并暂设 `target_surronding_id=None`（保留官方变量拼写）。由 `tools/init_configs.py` 生成 `target_id` 和 `select_obj_id` 数组；编号只作示例，实际必须从当前场景读取。
4. 先渲染或查看每个目标的删除范围，确认后再运行修复。如果看数字选对象过于低效，可另写一个读取现有标签图的鼠标点击小脚本；**不把点击 UI 作为 MVP 前置条件**。

**多目标删除规则**：按对象分别计算 `mask3d_i = threshold_i | convex_hull_i`，最终仅删除 `M_remove = OR_i(mask3d_i)`。**禁止把多个分散目标的所有 Gaussian 一起计算一个大凸包作为删除集合**，否则可能把中间的地面、货架一起误删。可以记录整体包围范围供轨迹规划，但它不是删除掩码。

**暂不启用周围对象临时移除**：官方 `edit_object_removal.py` 的部分恢复路径调用 `combine_gaussian(..., select_obj_id)`，而函数用该列表跳过重新加入的对象；`edit_object_inpaint.py` 的恢复条件又要求 `len(surrounding_ids)>1`。这使“目标删除”和“周围物体临时移除再恢复”尚不能等价看待。MVP-B 先只传入真正要删除的 ID，验证实际保留集合；如确需临时移除周围物体，单列实验，先校正恢复逻辑并验证 Keep 对象仍在。

### Run 0：对象感知基线

按官方流程得到带对象特征的 checkpoint，并以它作为 Run 0、Run 1 和 Run 2 的共同起点。删除阶段依赖该 checkpoint 中的对象特征；不要把更早的 Vanilla 3DGS checkpoint 与后两次运行直接比较。保存 Vanilla 训练结果作为附加参考即可，同时记录对象特征蒸馏的代码版本、训练日志、实际训练/测试视角列表和 checkpoint 路径。

### Run 1：仅删除

使用官方流程产生目标删除集合（MVP-A 为一个 ID，MVP-B 为多个 ID），先完成所有交互式 mask 修正和人工核验，再冻结本轮最终集合。官方代码不会自动保存删除索引，
因此需要在 `edit_object_removal.py` 的 `removal_setup` 附近加一个最小保存脚本，
按每个目标分别保存以下三个数组：阈值初筛 `obj_prob > removal_thresh`、凸包扩张后的
`mask3d_convex`，以及该目标的最终集合 `mask3d = threshold | convex_hull`；MVP-B 另保存所有目标 Mask 的并集。这些数组
必须对应同一个原始 Gaussian 顺序；不能用删除前后 PLY 的坐标近邻差集冒充稳定身份。

从同一个对象感知 checkpoint 应用这个已冻结的集合，生成正式 Run 1 删除结果。在不设置周围临时移除对象的 MVP-A/B 中，Run 1 快照应取
`point_cloud_object_removal/iteration_<N>/point_cloud.ply`；不要误用仅在周围对象恢复分支生成的 `*_removal_target` 合并结果。MVP-B 需要记录每个 ID 的 Gaussian 数量、各 Mask 的重叠量和并集大小，以便发现误删。保存删除后的 PLY、上述三个掩码、实际删除集合和固定视角渲染。

交互式修正期间产生的删除结果只能作为 `Run1-pre-refine` 诊断快照，不能作为正式
Run 1 对照。若修正改变了删除范围，丢弃或单独保留旧快照，重新从同一个对象感知
checkpoint 生成正式 Run 1；正式 Run 1 与 Run 2 必须使用同一份冻结掩码和同一份
实际删除集合。两次运行都要记录掩码版本，不能用一个模糊的“目标名称”代替输入。

官方删除脚本通常只渲染训练/测试相机，不渲染清场 `test_IMG_*` 对应的
`getInpaintCameras()`。因此必须增加一个最小渲染脚本，复用官方
`render_set_inpaint`（或 `edit_object_inpaint.py` 中等价调用），对 Run 0 和 Run 1
分别渲染清场视角；否则 Run 1 无法与真实清场参考做修复区域对照。

### Run 2：官方默认修复

使用本轮已经冻结、且与正式 Run 1 完全相同的目标集合和删除结果，运行官方 Inpaint360GS 默认修复流程。尤其对 MVP-B，核对修复阶段重新计算的删除集合与 Run 1 的集合是否一致；不一致时停止直接比较，先修正输入或将其标记为单独诊断实验，不能把质量差异只归因于 inpainting：

1. 准备虚拟视角数据；
2. LaMa 补 RGB 和深度；
3. 点云/深度融合；
4. Gaussian 优化；
5. 渲染评测结果。

首次运行保持官方默认配置，递归条件补全关闭。不要同时修改 NBS、inpainting 模型、损失权重或优化范围。官方虚拟相机轨迹及 `target_object_radius` 可能无法覆盖相距较远的多个空洞；MVP-B 先记录覆盖不足的情况，不预先开发分区轨迹系统。

注意：官方流程的对象关联和删除可能包含目标 ID、周边对象或包络筛选。MVP 必须记录最终实际删除集合，不能只记录用户选择的对象名称。

## 4. 评测

### 必须保存的结果

- Run 0、Run 1、Run 2 的 checkpoint/PLY；
- 官方实际删除 Gaussian 集合；MVP-B 还须保存每个目标 Mask 及并集、各目标位置和多区域修复前后对比；
- 每个结果在官方测试视角和 `test_IMG_*` 上的渲染；
- `unseen_mask` 对应的修复区域结果；
- 官方配置、代码 commit、权重和运行日志；
- 一份固定轨迹视频或逐视角对比图。
- 固定清场视角上的 Run 0、Run 1、Run 2 与 `test_IMG_*` 并排图；至少包含一组能看出修复区域的对照。
- 每一步的开始/结束时间、峰值 GPU 显存和失败日志；至少覆盖 Run 0、删除步骤和 Run 2 的 LaMa/优化步骤。

### 比较关系

| 比较 | 回答的问题 |
|---|---|
| Run 1 vs `test_IMG_*`，修复区域 | 仅删除的下界，删除后缺失多少真实背景 |
| Run 2 vs `test_IMG_*`，修复区域 | 官方修复是否恢复了真实清场背景 |
| Run 2 vs Run 1，非修复区域 | 修复过程是否改坏了未编辑背景 |
| Run 0 / Run 1 / Run 2，带物体留出视角 | 未参与优化的原始场景视角是否保持一致 |

优先使用官方 `metrics_fid_masked.py` 生成论文口径的对照结果。该脚本会报告 masked、non-masked 和 full 指标，并在找不到 mask 时显式提示。

官方 masked 指标通过将非目标区域置零后计算，不能直接等同于严格的“只对 mask 像素计算”。因此 MVP 还应保存 mask 位置、mask 极性和脚本版本；若官方结果出现异常，再补一个按有效 mask 像素筛选的独立区域误差计算。

没有必要在 MVP 阶段设定最终 PSNR、LPIPS 或 FID 通过阈值。先比较三组结果，记录绝对值、差值和失败案例。MVP-B 分目标区域报告残留、误删及修复效果；只有确认真实清场 GT 覆盖该目标时才计算对应真实性指标，避免用单目标 GT 为多目标修复背书。

## 5. 判断规则

分别报告 **MVP-A（单目标基线）** 与 **MVP-B（多目标清理）** 的结论。MVP-A 是首轮必需的修复闭环；只有 A 完成并通过输入一致性检查后才执行 B。A 成功不等于多目标场景净化已经成立；B 如果缺少全部目标的清场 GT，只能报告多目标删除与视觉连续性的结论，不得宣称全部隐藏背景已真实恢复。

### 值得继续

- Run 1 没有明显误删受保护背景；
- Run 2 在真实清场参考的修复区域上优于 Run 1，或明显改善结构连续性；
- Run 2 的 non-masked 区域没有出现不可接受的退化；
- 失败可以定位到具体环节，而不是输入或评测不明；
- MVP-B 中多个目标均被删除、目标间 Keep 区域没有明显误删，且每个待修复区域均被实际检查（覆盖不足也如实记录）。

### 暂停或转向

- Run 1 已经大面积误删背景，先修目标归属和删除集合；
- Run 2 不优于 Run 1，且失败集中在官方修复流程本身；
- 结果只能在带物体图像上比较，缺少真实清场参考，无法回答背景是否恢复。

### 实验受阻，待排查

官方数据、配置、权重、CUDA 扩展或 conda 环境无法按固定流程运行时，只记录为实验受阻，
不要据此否定修复路线。先保存错误日志、环境版本和失败步骤，修复环境后再继续同一实验。

- [ ] 为 Run 0/Run 1 补充基于 `getInpaintCameras()` 的清场视角渲染。
- [ ] 确认 Run 0、Run 1、Run 2 使用同一个对象感知 checkpoint，并保留 Run 1 快照后再继续交互流程。
- [ ] 先完成交互式修正并冻结最终删除集合，再从同一 checkpoint 分别生成正式 Run 1 和 Run 2；修正前结果标记为 `Run1-pre-refine`。
- [ ] MVP-A 的目标 ID 已人工核验；MVP-B 的多个 ID、逐目标 Mask/并集、Keep 对象及参考图像覆盖范围已核验。
- [ ] MVP-B 默认不传周围临时移除对象；需要此能力时先修正并验证官方恢复逻辑，不将其与多目标删除混为一谈。

## 7. MVP 之后再做什么

完成 MVP-A，并在条件允许时完成 MVP-B（或明确记录 B 因数据不满足而无法评测）后，根据实际失败位置选择一个方向：

- 删除集合错误：做 2D mask → 3D Gaussian 的可控分离和人工复核；
- 修复区域错误：研究 NBS、可见性和深度可靠性；
- 背景被改坏：实现可靠区域冻结和局部优化；
- 官方流程有效但无法接收外部选择：实现 `ExternalSelection` 适配；
- 仅 PLY 需求明确且完整数据效果成立：再做 PLY-only 降级路径。

MVP 的代码可以只是官方脚本、少量运行记录和一个结果汇总脚本。只有实验暴露出稳定、重复出现的需求，才把它提升为正式接口或工程协议。
