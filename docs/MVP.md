# GSCleaner MVP 验证方案

> 目标：用一个官方 Inpaint360GS 场景，验证“给定正确目标后，删除并修复是否值得继续投入”。
>
> 本文是首轮技术验证方案，不是最终产品设计。首轮只验证完整数据条件下的背景清理，不实现编辑器、通用适配器、自动候选或 PLY-only 高质量修复。

## 1. MVP 要回答的问题

给定一个人工核验的目标对象：

1. 仅删除目标后，是否会误删目标周围的背景？
2. 官方 Inpaint360GS 修复是否比“仅删除”更接近真实的清场背景？
3. 修复是否破坏了原本没有被编辑的区域？
4. 主要失败来自目标归属、空洞判断，还是补全质量？

单个场景只能形成局部结论：成功说明值得在更多场景继续，失败说明当前配置或方法在该场景上不成立，不能直接推广到所有场景。

## 2. 固定范围

### 使用的数据

选择一个官方 `inpaint360` 场景，要求数据目录同时包含：

- 带干扰物的训练图像、COLMAP 相机和官方配置；
- `test_IMG_*` 清场后的图像，用作真实背景参考；
- 数据目录中的 `unseen_mask`，用于修复区域评测；它是否确实是人工核验的清场区域，必须在运行前检查。

官方代码对 `inpaint360` 数据会把包含 `test` 的图像排除在训练图像之外，并在 `--eval` 下从带物体图像中按 `llffhold=8` 留出测试视角。运行时不要改动官方数据布局或绕过这套划分。

`unseen_mask` 有两条可能的来源路径，不能混为一谈：数据集目录中的
`data/inpaint360/<scene>/unseen_mask/` 是评测参考；运行修复流程生成的
`inpaint_2d_unseen_mask_virtual/` 是管线中间产物。后者不能自动视为真实 GT，
也不能用管线自己生成的 mask 证明管线输出正确。开始 Run 0 前应打开几张数据集
`unseen_mask`，确认文件名能覆盖计划评测的 `test_IMG_*` 视角，确认前景/背景
极性、分辨率和区域含义，并把这次核验结果记录下来。若 mask 只覆盖虚拟视角，
必须调整评测设计，不能声称 Run 1 也有同等区域评测。

这里有两类评测参考：

- `test_IMG_*`：清场后的真实图像，用于判断背景恢复是否接近真实结果；
- `--eval` 留出的带物体视角：用于检查未参与优化的原始场景视角上的一致性。

它们不是同一个测试集，必须分别记录。

### 暂不实现

- SuperSplat/LichtFeld 集成和 UI；
- `RemovalAdapter`、稳定 ID 谱系和通用 schema；
- 自动发现干扰物；
- PLY-only 的高质量补全；
- 阴影、反射、重光照和碰撞 mesh；
- 完整产品阈值和跨场景统计结论。

## 3. 三次运行

三次运行必须使用相同场景、相同训练配置、相同目标和可比的相机设置。

### Run 0：原始基线

按官方流程训练未编辑的原始 3DGS，得到原始 checkpoint 和渲染结果。保存训练日志、实际训练/测试视角列表和 checkpoint 路径。

### Run 1：仅删除

使用官方流程产生并人工核验一个目标删除集合。官方代码不会自动保存删除索引，
因此需要在 `edit_object_removal.py` 的 `removal_setup` 附近加一个最小保存脚本，
至少保存以下三个数组：阈值初筛 `obj_prob > removal_thresh`、凸包扩张后的
`mask3d_convex`，以及最终删除集合 `mask3d = threshold | convex_hull`。这三者
必须对应同一个原始 Gaussian 顺序；不能用删除前后 PLY 的坐标近邻差集冒充稳定身份。

从同一个原始 checkpoint 应用该集合，只执行删除，不执行补全和修复。实际操作上，
先运行官方 `run_remove.sh`，在删除结果（`combined_gaussian_path`）生成后停止，
不要继续执行交互式 refine，也不要运行 `run_inpaint.sh`。保存删除后的 PLY、上述
三个掩码、实际删除集合和固定视角渲染。

### Run 2：官方默认修复

使用同一目标和同一删除结果，运行官方 Inpaint360GS 默认修复流程：

1. 准备虚拟视角数据；
2. LaMa 补 RGB 和深度；
3. 点云/深度融合；
4. Gaussian 优化；
5. 渲染评测结果。

首次运行保持官方默认配置，递归条件补全关闭。不要同时修改 NBS、inpainting 模型、损失权重或优化范围。

注意：官方流程的对象关联和删除可能包含目标 ID、周边对象或包络筛选。MVP 必须记录最终实际删除集合，不能只记录用户选择的对象名称。

## 4. 评测

### 必须保存的结果

- Run 0、Run 1、Run 2 的 checkpoint/PLY；
- 官方实际删除 Gaussian 集合；
- 每个结果在官方测试视角和 `test_IMG_*` 上的渲染；
- `unseen_mask` 对应的修复区域结果；
- 官方配置、代码 commit、权重和运行日志；
- 一份固定轨迹视频或逐视角对比图。
- 每一步的开始/结束时间、峰值 GPU 显存和失败日志；至少覆盖 Run 0、删除步骤和 Run 2 的 LaMa/优化步骤。

### 比较关系

| 比较 | 回答的问题 |
|---|---|
| Run 1 vs `test_IMG_*`，修复区域 | 仅删除的下界，删除后缺失多少真实背景 |
| Run 2 vs `test_IMG_*`，修复区域 | 官方修复是否恢复了真实清场背景 |
| Run 2 vs Run 1，非修复区域 | 修复过程是否改坏了未编辑背景 |
| Run 0 / Run 1 / Run 2，带物体留出视角 | 未参与优化的原始场景视角是否保持一致 |

优先使用官方 `metrics_fid_masked.py` 生成论文口径的对照结果。该脚本会报告 masked、non-masked 和 full 指标，并在找不到 mask 时显式提示。

官方 masked 指标通过将非目标区域置零后计算，不能直接等同于严格的“只对 mask 像素计算”。因此 MVP 还应保存 mask 位置、mask 极性和脚本版本；若官方结果出现异常，再补一个按有效 mask 像素筛选的独立区域误差计算。

没有必要在 MVP 阶段设定最终 PSNR、LPIPS 或 FID 通过阈值。先比较三组结果，记录绝对值、差值和失败案例。

## 5. 判断规则

### 值得继续

- Run 1 没有明显误删受保护背景；
- Run 2 在真实清场参考的修复区域上优于 Run 1，或明显改善结构连续性；
- Run 2 的 non-masked 区域没有出现不可接受的退化；
- 失败可以定位到具体环节，而不是输入或评测不明。

### 暂停或转向

- Run 1 已经大面积误删背景，先修目标归属和删除集合；
- Run 2 不优于 Run 1，且失败集中在官方修复流程本身；
- 官方数据、配置、权重或环境无法按固定流程运行；
- 结果只能在带物体图像上比较，缺少真实清场参考，无法回答背景是否恢复。

## 6. MVP 之后再做什么

根据首轮失败位置选择一个方向：

- 删除集合错误：做 2D mask → 3D Gaussian 的可控分离和人工复核；
- 修复区域错误：研究 NBS、可见性和深度可靠性；
- 背景被改坏：实现可靠区域冻结和局部优化；
- 官方流程有效但无法接收外部选择：实现 `ExternalSelection` 适配；
- 仅 PLY 需求明确且完整数据效果成立：再做 PLY-only 降级路径。

MVP 的代码可以只是官方脚本、少量运行记录和一个结果汇总脚本。只有实验暴露出稳定、重复出现的需求，才把它提升为正式接口或工程协议。
